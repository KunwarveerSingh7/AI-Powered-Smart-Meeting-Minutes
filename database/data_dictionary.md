# Database Data Dictionary

## Project

AI-Powered Smart Meeting Minutes and Task Management System

## Database Technology

SQLite with SQLAlchemy ORM.

The database stores users, uploaded meetings, AI-generated summaries and
decisions, tasks, task assignments and employee progress updates.

---

## 1. Users Table

Table name: `users`

This table is already partly implemented by the authentication team.

| Field | Data Type | Constraints | Description |
|---|---|---|---|
| id | Integer | Primary key, auto-increment | Unique user identifier |
| email | String(255) | Unique, not null, indexed | User login email |
| hashed_password | String(255) | Not null | Securely hashed user password |
| role | String(20) | Not null, default employee | User role: manager or employee |

### Relationships

- One user can upload many meetings.
- One user can be assigned to many tasks.
- One user can create many task updates.

---

## 2. Meetings Table

Table name: `meetings`

This table stores uploaded meeting documents, extracted text, AI summaries and
publication status.

| Field | Data Type | Constraints | Description |
|---|---|---|---|
| id | Integer | Primary key, auto-increment | Unique meeting identifier |
| title | String(255) | Not null | Meeting title |
| meeting_date | DateTime | Nullable | Date and time of the meeting |
| uploaded_by | Integer | Foreign key to users.id, not null | Manager who uploaded the meeting |
| original_filename | String(255) | Not null | Original uploaded file name |
| stored_file_path | String(500) | Not null | Local path of the uploaded file |
| file_type | String(20) | Nullable | Uploaded file type, such as PDF, DOCX or TXT |
| raw_text | Text | Nullable | Text extracted from the uploaded document |
| ai_summary | Text | Nullable | Summary generated by the local AI model |
| status | String(20) | Not null, default draft | Meeting status: draft, published or archived |
| created_at | DateTime | Not null | Record creation date and time |
| updated_at | DateTime | Not null | Most recent record update |
| published_at | DateTime | Nullable | Date and time the manager published the meeting |

### Relationships

- One user can upload many meetings.
- One meeting can contain many decisions.
- One meeting can contain many tasks.

---

## 3. Decisions Table

Table name: `decisions`

This table stores decisions identified from a meeting document.

| Field | Data Type | Constraints | Description |
|---|---|---|---|
| id | Integer | Primary key, auto-increment | Unique decision identifier |
| meeting_id | Integer | Foreign key to meetings.id, not null | Meeting connected to the decision |
| decision_text | Text | Not null | Description of the identified decision |
| created_at | DateTime | Not null | Decision record creation time |

### Relationships

- One meeting can contain many decisions.
- Each decision belongs to one meeting.

---

## 4. Tasks Table

Table name: `tasks`

This table stores action items generated from meeting documents and reviewed by
the manager.

| Field | Data Type | Constraints | Description |
|---|---|---|---|
| id | Integer | Primary key, auto-increment | Unique task identifier |
| meeting_id | Integer | Foreign key to meetings.id, not null | Meeting from which the task was created |
| title | String(255) | Not null | Short task title |
| description | Text | Nullable | Detailed task description |
| due_date | DateTime | Nullable | Task deadline |
| priority | String(20) | Not null, default medium | Priority: low, medium or high |
| status | String(20) | Not null, default pending | Status: pending, in_progress, completed or cancelled |
| created_at | DateTime | Not null | Task creation date and time |
| updated_at | DateTime | Not null | Most recent task update |

### Relationships

- One meeting can contain many tasks.
- One task can be assigned to one or more users.
- One task can contain many progress updates.

---

## 5. Task Assignments Table

Table name: `task_assignments`

This table connects users and tasks. A separate assignment table allows one task
to be assigned to more than one employee.

| Field | Data Type | Constraints | Description |
|---|---|---|---|
| id | Integer | Primary key, auto-increment | Unique assignment identifier |
| task_id | Integer | Foreign key to tasks.id, not null | Assigned task |
| user_id | Integer | Foreign key to users.id, not null | Assigned employee |
| assigned_at | DateTime | Not null | Assignment creation date and time |

### Additional Constraint

The combination of `task_id` and `user_id` must be unique so the same employee
cannot be assigned to the same task twice.

### Relationships

- One task can have many task assignments.
- One user can have many task assignments.

---

## 6. Task Updates Table

Table name: `task_updates`

This table stores employee progress updates and provides a task activity history.

| Field | Data Type | Constraints | Description |
|---|---|---|---|
| id | Integer | Primary key, auto-increment | Unique update identifier |
| task_id | Integer | Foreign key to tasks.id, not null | Updated task |
| updated_by | Integer | Foreign key to users.id, not null | User who submitted the update |
| status | String(20) | Not null | Task status after the update |
| progress_percentage | Integer | Not null, default 0 | Task completion value from 0 to 100 |
| comment | Text | Nullable | Employee progress note |
| created_at | DateTime | Not null | Update creation date and time |

### Relationships

- One task can contain many updates.
- One user can create many task updates.

---

## Analytics

A separate analytics table is not required for the first prototype.

Dashboard information will be calculated using database queries, including:

- Total meetings
- Total tasks
- Pending tasks
- Tasks in progress
- Completed tasks
- Overdue tasks
- Task completion percentage
- Tasks assigned to each employee

An overdue task will be calculated when its due date has passed and its status is
not completed or cancelled.

---

## Prototype Scope Decisions

- One uploaded document will represent one meeting.
- Supported document types will be PDF, DOCX and TXT.
- Managers will review AI-generated content before publishing it.
- JWT authentication will be used, so a database session table is not required.
- SQLite database files will remain local and will not be uploaded to GitHub.
